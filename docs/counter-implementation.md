# Counter and menu implementation

F1 is on `/order`. It uses the shared Beans&Beats design and the merged schema.

## Setup

Apply `20261106010000_counter_orders.sql` after the existing migrations in a disposable database first. Follow the README's migration-history warning for the hosted project; do not replay already applied migrations. Set `SUPABASE_SERVICE_ROLE_KEY` and a random `STAFF_SESSION_SECRET` (at least 32 characters) on the server, in addition to the existing Supabase URL. Never expose either secret through a `NEXT_PUBLIC_` variable. No credentials are committed or generated by the app.

The temporary sign-in boundary uses the merged `verify_staff_credentials` function and administrator-provisioned username accounts. The cookie is signed, HttpOnly, SameSite Strict, secure in production and expires after 12 hours. Each protected request rechecks the active staff row and role. Sign-in is limited to ten attempts per username per 15 minutes in Postgres. Remove public-password mock accounts before using a live or judge environment.

`src/lib/staff-server.ts` is the single session boundary to replace when TL's F17 implementation lands. This implements access for the counter/menu workspace only, not all of F17 or F16. No public registration, role editor, offline sign-in or privileged browser database client is introduced. Existing legacy `counter` accounts are accepted alongside `barista` and `admin`; new shared staff accounts can be `barista`.

## Order flow and assumptions

- New orders are online only. An existing open screen can retain/edit its draft during an outage; it does not promise a cold offline page load or transmit between offline devices. No automatic submission on reconnection.
- Drafts are retained in this tab's session storage, keyed by staff ID, through reload and reauthentication. A different account does not see that draft through the UI. Storage failure blocks submission rather than losing the retry ID. Closing the tab ends this draft storage; F16 can replace it with the agreed durable offline store.
- Staff take POS payment, then submit. A changed price or unavailable selection blocks submission and asks staff to reconcile the POS payment. The app never processes payment or silently accepts a different total.
- An ambiguous submission is locked for retry with its exact original payload and request ID, including after reload. The database returns the same receipt for the same request. Different data cannot reuse an accepted request ID. Successful confirmation clears the draft only after the receipt is retained.
- The database allocates numeric pickup numbers atomically for each Singapore date and inserts the order/items/snapshots in one transaction. `queued` is the stored status for the UI's Received state. Historical snapshots are immutable to these menu/order endpoints.
- Menu data polls every three seconds while visible and refreshes on edits, focus visibility and reconnection. Final order validation is in the database. Sold-out drinks remain visible; inactive drinks are hidden.
- Only the existing iced and oat-milk options are offered. Oat milk is permitted on latte and flat white only. Option editing/creation is deferred (story 30).
- Optional mobile numbers must be Singapore mobiles and have explicit consent for staff order follow-up. Consent time is stored; no SMS is sent. F18 still owns the complete retention/cleanup policy. No customer details are sent to logs or public order endpoints by this work.
- A receipt includes order identity, pickup number, date, line snapshots and charged total. Tracking QR rendering is left to TL's F7; no new collection-token contract is invented.

## Endpoints

All counter endpoints require the staff session; writes also require a matching Origin. Responses are `no-store`. Roles come from the trusted database record, never request data.

- `GET /api/staff/session`, `POST /api/staff/session`, `DELETE /api/staff/session`: check, sign in and sign out.
- `GET /api/counter/menu`: complete staff menu, including sold-out/inactive records for role-appropriate presentation.
- `POST /api/counter/orders`: `{ draft, totalCents }`; accepts first name, optional mobile/consent and item IDs/quantities/options. Actor identity is supplied by the server. Returns the immutable receipt. SQL functions are executable only by the server service role.

## F10 price controls

The admin menu screen edits drink base prices and existing option surcharges. Baristas can read prices but cannot mutate them. PATCH `/api/counter/menu` accepts `{kind, id, version, action: "price", value: "9.00"}`. The server parses decimal SGD input into cents; Postgres compares the expected version while locking the row. A conflicting edit is retained until the admin explicitly reviews the current value. Identical retry values are safe; no silent overwrite, price rounding or history mutation occurs. Apply `20261106020000_counter_prices.sql` after the F1 migration. `supabase/tests/counter_prices.sql` verifies permissions, version conflicts, retries and shared option prices.

## F11 availability controls

Baristas and admins can set drinks to Sold out/Available and existing options to Unavailable/Available. Legacy counter-only accounts keep order-entry access but cannot edit availability. Changes name the desired state (never a blind toggle), retain that choice on failure and require review if the item's version changed. Inactive drinks cannot be restored through availability. Unavailable oat milk is disabled on all drinks offering it, while other choices remain orderable. Existing orders and prices are untouched. All availability writes require a connection.

Apply `20261106030000_counter_availability.sql` next. PATCH `/api/counter/menu` also accepts `{kind, id, version, action: "availability", value: false}`. Run `supabase/tests/counter_availability.sql` for desired-state retries, staff permissions, conflicts and inactive-item protection. The same permission rules are enforced in both the API and SQL.

## F12 deactivation controls

Only admins see Deactivate drink. The confirmation names the drink, explains that existing orders/history stay intact, and offers Keep drink active. A confirmed save sets `is_active = false`; the record remains labelled Inactive in admin controls and disappears from order entry and barista menu controls. There is no delete or reactivation endpoint. Stale confirmations require review, retries are harmless and offline deactivation is blocked.

Apply `20261106040000_counter_deactivation.sql` last. PATCH `/api/counter/menu` accepts `{kind: "drink", id, version, action: "deactivate", value: false}`. The SQL suite `supabase/tests/counter_deactivation.sql` verifies permissions, retained rows/receipts, retry safety, order rejection and prevention of reactivation through availability.
